3. Phase 1: Generate and Prepare Burp Suite CA Certificate

Step 1: Export Burp's CA Certificate

Open Burp Suite → Proxy → Options → Import/Export CA Certificate → Export Certificate in DER format → Save as cacert.der

Step 2: Convert DER to PEM Format

openssl x509 -inform DER -in cacert.der -out cacert.pem

What this does: Converts the Burp CA certificate from DER (binary) format to PEM (Base64 text) format. Android's certificate store requires PEM format with a specific filename.

Breakdown:

  • openssl x509 — OpenSSL's X.509 certificate utility
  • -inform DER — Input format is DER (Distinguished Encoding Rules, binary)
  • -in cacert.der — Input file (exported from Burp)
  • -out cacert.pem — Output file in PEM format

Step 3: Get the Certificate Hash

openssl x509 -inform PEM -subject_hash_old -in cacert.pem | head -1

What this does: Calculates the "old-style" hash of the certificate's subject name. Android uses this hash as the filename for system CA certificates.

Breakdown:

  • -subject_hash_old — Generates the OpenSSL "old" hash (Android uses this, not the new hash)
  • | head -1 — Takes only the first line of output (the hash itself), ignoring the certificate content that follows

Output in our case: 9a5ba575

Step 4: Rename Certificate File

cp cacert.pem 9a5ba575.0

What this does: Copies the PEM certificate and renames it to <hash>.0. Android's system certificate store expects certificates named as <subject_hash>.0. The .0 suffix is an index — if multiple certificates had the same hash, they'd be .0, .1, .2, etc.

4. Phase 2: Push Certificate to Emulator (Initial Attempts)

Attempt 1: Standard adb remount (FAILED)

adb -s emulator-5554 root
adb -s emulator-5554 remount
adb -s emulator-5554 push 9a5ba575.0 /system/etc/security/cacerts/
adb -s emulator-5554 shell chmod 644 /system/etc/security/cacerts/9a5ba575.0
adb -s emulator-5554 reboot

What each command does:

  • adb root — Restarts the ADB daemon on the device with root privileges
  • adb remount — Remounts the /system partition as read-write (normally it's read-only for security)
  • adb push <file> <path> — Copies a file from your computer to the Android device
  • chmod 644 — Sets file permissions: owner can read/write (6), group and others can only read (4,4). This is required so all apps can read the certificate
  • reboot — Restarts the emulator to apply changes

Result: remount failed — The system partition couldn't be remounted due to I/O errors and overlayfs issues. This is common on newer emulator images.

Attempt 2: User Certificate Store (WORKED but insufficient)

adb -s emulator-5554 push 9a5ba575.0 /sdcard/

What this does: Pushes the certificate to the SD card, which is always writable.

Then in the adb shell:

su
mkdir -p /data/misc/user/0/cacerts-added/
cp /sdcard/9a5ba575.0 /data/misc/user/0/cacerts-added/
chmod 644 /data/misc/user/0/cacerts-added/9a5ba575.0
reboot

What each command does:

  • mkdir -p /data/misc/user/0/cacerts-added/ — Creates the directory for user-installed CA certificates. The 0 refers to user ID 0 (primary user). -p creates parent directories if they don't exist
  • cp /sdcard/9a5ba575.0 ... — Copies the certificate from SD card to the user CA store
  • chmod 644 — Sets correct read permissions
  • reboot — Restarts to apply

Result: Certificate installed in user store, but the app's network_security_config with debugBuild: false means it only trusts system CAs, not user-installed ones. The native OkHttp layer showed SSLHandshakeException: Trust anchor for certification path not found.

Attempt 3: Mount /system as Read-Write (FAILED)

adb -s emulator-5554 shell
su
mount -o rw,remount /system

What this does: Attempts to remount the /system partition with read-write access directly from the shell.

Result: mount: '/system' not in /proc/mounts — On system-as-root emulators, /system isn't a separate mount point.

Attempt 4: Remount Root Filesystem (FAILED)

mount -o rw,remount /

What this does: Attempts to remount the root filesystem as read-write, which on system-as-root devices includes /system.

Result: '/dev/block/dm-0' is read-only — The device-mapper block device is enforced as read-only.

5. Phase 3: Writable System Attempts

Attempt 5: Launch Emulator with -writable-system Flag

First, find your AVD name:

emulator -list-avds

What this does: Lists all available Android Virtual Devices configured on your system.

Output:

android_11_root
non_rooted

Then launch with writable system:

emulator -avd android_11_root -writable-system -no-snapshot-load

What each flag does:

  • -avd android_11_root — Specifies which AVD to launch
  • -writable-system — Makes the system partition writable, allowing modifications to /system
  • -no-snapshot-load — Forces a cold boot instead of loading a saved snapshot. This ensures the writable system flag takes effect from a clean state

Note: First boot with these flags can take 2-5 minutes on ARM emulators. Wait until adb devices shows device instead of offline.

Attempt 6: adb remount After -writable-system (FAILED)

adb -s emulator-5554 root
adb -s emulator-5554 remount

Result: Still failed with the same overlayfs I/O errors. This particular system image has issues with the remount mechanism.

Attempt 7: Disable Verity + Remount (FAILED)

adb -s emulator-5554 disable-verity
adb -s emulator-5554 reboot
adb -s emulator-5554 root
adb -s emulator-5554 remount

What each command does:

  • disable-verity — Disables dm-verity, Android's verified boot mechanism that ensures the system partition hasn't been modified. Returns "Successfully disabled verity"
  • reboot — Required for verity changes to take effect
  • root + remount — Attempt to remount again after verity is disabled

Result: disable-verity succeeded, but remount still failed. Even without verity, the overlayfs mechanism couldn't be set up on this image.

6. Phase 4: tmpfs Overlay Method (Working Approach)

This is the method that successfully placed the Burp CA certificate in the system trust store without needing to modify the read-only system partition.

Step 1: Push Certificate to SD Card

adb -s emulator-5554 push 9a5ba575.0 /sdcard/

What this does: Copies the prepared certificate file from your Mac to the emulator's SD card, which is always writable.

Step 2: Create tmpfs Overlay

adb -s emulator-5554 shell
su

What this does: Opens a root shell on the emulator.

mkdir -p /dev/tmp_certs

What this does: Creates a temporary directory in /dev (which is always writable, stored in RAM) to stage our certificates.

cp /system/etc/security/cacerts/* /dev/tmp_certs/

What this does: Copies ALL existing system CA certificates to our staging directory. This is critical — we need to preserve all the original certificates, otherwise the device won't be able to make any HTTPS connections at all.

cp /sdcard/9a5ba575.0 /dev/tmp_certs/

What this does: Adds our Burp Suite certificate alongside the existing system certificates in the staging directory.

chmod 644 /dev/tmp_certs/*

What this does: Sets proper read permissions on all certificates so any app can read them.

mount -t tmpfs tmpfs /system/etc/security/cacerts

What this does: This is the key trick. It mounts a tmpfs (temporary filesystem stored in RAM) on top of the existing /system/etc/security/cacerts directory. This "shadows" the original read-only directory with a writable RAM-based one. The original files underneath are untouched — they're just hidden by the overlay.

Breakdown:

  • mount -t tmpfs — Mount a filesystem of type tmpfs (RAM-based)
  • tmpfs — The device name (for tmpfs, this is just a label)
  • /system/etc/security/cacerts — The mount point (where to overlay)
cp /dev/tmp_certs/* /system/etc/security/cacerts/

What this does: Copies all certificates (original + Burp) into the newly mounted tmpfs. Now the system certificate store contains everything it had before, plus our Burp certificate.

chmod 644 /system/etc/security/cacerts/*

What this does: Sets read permissions again on the files in their final location.

chcon u:object_r:system_security_cacerts_file:s0 /system/etc/security/cacerts/*

What this does: Sets the correct SELinux security context on all certificate files. Android uses SELinux (Security-Enhanced Linux) for mandatory access control. Even if Unix file permissions allow access, SELinux can still block it if the context is wrong.

Breakdown:

  • chcon — Change SELinux context
  • u:object_r:system_security_cacerts_file:s0 — The SELinux label that Android expects on system CA certificate files:
    • u — SELinux user
    • object_r — SELinux role for files
    • system_security_cacerts_file — The type that grants read access to apps checking system CAs
    • s0 — Sensitivity level

Step 3: Verify the Certificate

ls -laZ /system/etc/security/cacerts/9a5ba575.0

What this does: Lists the file with detailed info including SELinux context (-Z flag).

Expected output:

-rw-r--r-- 1 root root u:object_r:system_security_cacerts_file:s0 1330 2026-05-05 22:28 /system/etc/security/cacerts/9a5ba575.0

What to verify:

  • Permissions: -rw-r--r-- (644)
  • Owner: root root
  • SELinux context: u:object_r:system_security_cacerts_file:s0
  • File size: Should be non-zero (1330 bytes in our case)

Important Notes About tmpfs Method

  • Not persistent across reboots — The tmpfs is in RAM, so it disappears on reboot. You must redo this process after each emulator restart
  • No system partition modification needed — Works even when the system partition is completely read-only
  • Preserves original certificates — All original system CAs remain functional
  • SELinux context is critical — Without the correct chcon, apps will get EACCES (Permission denied) even though file permissions look correct

7. Phase 5: Traffic Redirection with iptables

Why iptables is Needed

Flutter/Dart applications use their own HTTP stack that ignores Android's system proxy settings. To force Flutter traffic through Burp Suite, we need to redirect it at the network level using iptables.

Set Up iptables Redirect Rules

adb -s emulator-5554 shell
su
iptables -t nat -A OUTPUT -p tcp --dport 443 -j DNAT --to-destination 10.0.2.2:8080
iptables -t nat -A OUTPUT -p tcp --dport 80 -j DNAT --to-destination 10.0.2.2:8080

What each command does:

Command 1 (HTTPS redirect):

  • iptables — Linux firewall/packet filtering tool
  • -t nat — Use the NAT (Network Address Translation) table
  • -A OUTPUT — Append a rule to the OUTPUT chain (outgoing traffic from the device)
  • -p tcp — Match TCP protocol
  • --dport 443 — Match traffic going to port 443 (HTTPS)
  • -j DNAT — Jump to DNAT target (Destination NAT — change where the packet goes)
  • --to-destination 10.0.2.2:8080 — Redirect to 10.0.2.2 port 8080

Command 2 (HTTP redirect): Same as above but for port 80 (HTTP).

About 10.0.2.2: This is a special IP address in the Android emulator that maps to 127.0.0.1 (localhost) on the host machine. So traffic destined for any HTTPS server gets redirected to Burp Suite running on your Mac.

Remove iptables Rules (if needed)

iptables -t nat -F OUTPUT

What this does: Flushes (removes) all rules in the OUTPUT chain of the NAT table. Use this if the iptables redirect is causing connection timeouts or if you want to switch to WiFi proxy mode.

8. Phase 6: WiFi Proxy Configuration

Why WiFi Proxy is Also Needed

Some apps (including Flutter apps using Dio) may not have their traffic caught by iptables rules in all cases. Setting the WiFi proxy provides an additional interception method.

Set WiFi Proxy via ADB

adb -s emulator-5554 shell settings put global http_proxy 10.0.2.2:8080

What this does: Sets the global HTTP proxy setting on the Android device to route through Burp Suite on your host machine.

Set WiFi Proxy via GUI

  1. Open Settings on the emulator
  2. Go to Network & internet → Wi-Fi
  3. Long press on AndroidWifi
  4. Tap Modify network
  5. Tap Advanced options
  6. Change Proxy to Manual
  7. Set:
    • Proxy hostname: 10.0.2.2
    • Proxy port: 8080
  8. Tap Save

Remove WiFi Proxy (when done testing)

adb -s emulator-5554 shell settings put global http_proxy :0

What this does: Clears the proxy setting by setting it to an empty host with port 0.

9. Phase 7: SELinux Context Fix

The Problem

Even after mounting the tmpfs and setting file permissions to 644, the app showed repeated errors:

DirectoryCertificateSrc: Failed to read certificate from 9a5ba575.0
java.io.FileNotFoundException: /system/etc/security/cacerts/9a5ba575.0: open failed: EACCES (Permission denied)

This happened because when files are copied to a tmpfs mount, they get the default SELinux context (usually u:object_r:tmpfs:s0) instead of the context Android expects for certificate files.

The Fix

adb -s emulator-5554 shell
su
chcon u:object_r:system_security_cacerts_file:s0 /system/etc/security/cacerts/*

What this does: Changes the SELinux context of all files in the cacerts directory to system_security_cacerts_file, which is the type that Android's NetworkSecurityConfig and TrustManagerImpl require to read certificate files.

Verify the Fix

ls -laZ /system/etc/security/cacerts/9a5ba575.0

Expected output should show the correct context:

-rw-r--r-- 1 root root u:object_r:system_security_cacerts_file:s0 1330 ...

Force-Stop and Relaunch the App

am force-stop com.oslmobile.global

What this does: Completely kills the app process. This is necessary because the app caches the certificate store in memory when it first starts. A simple reopen from the app drawer would use the cached (broken) certificate list. Force-stopping ensures a fresh start that reads the corrected certificates.

10. Phase 8: Burp Suite Configuration

Listener Setup

Burp Suite needs two listeners configured:

  1. Local listener: 127.0.0.1:8080 (for WiFi proxy connections)
  2. Network listener: <your-IP>:8080 (e.g., 192.168.1.104:8080 for direct connections)

Enable Invisible Proxying

For the iptables redirect to work, Burp must support "invisible" proxying because the redirected traffic doesn't contain a proxy CONNECT header.

  1. Go to Proxy → Options (or Proxy Settings)
  2. Edit your listener (the one on port 8080)
  3. Go to Request handling tab
  4. Check "Support invisible proxying (enable only if needed)"
  5. Click OK

Bind to All Interfaces

Make sure Burp listens on all interfaces:

  1. Edit the listener
  2. Under Bind to address, select "All interfaces"

11. Observations and Challenges

What We Discovered During Testing

1. Flutter/Dart Ignores System Proxy Flutter's Dart HTTP client (Dio) does not respect Android's WiFi proxy settings. It also uses its own SSL/TLS implementation compiled into libflutter.so, which means it doesn't use the Android system certificate store for certificate validation.

2. Flutter/Dart Ignores System Certificate Store Even with the Burp cert in the system store, Flutter's Dart layer makes direct connections. The logcat showed Flutter requests succeeding with statusCode: 200 while native OkHttp requests were failing with SSL errors — proving the two layers use different trust stores.

3. Native OkHttp Layer Uses System Store The app's native layer (Checkout.com Risk SDK, Glide image loading, Firebase) uses OkHttp which respects the Android NetworkSecurityConfig. When the system cert was properly installed with correct SELinux context, these calls should work through Burp.

4. The App Has network_security_config with debugBuild: false This means the app only trusts system CAs in production — user-installed certificates are rejected. This is why the user cert store approach was insufficient.

5. SELinux Enforcement Even though we confirmed permissive=0 (enforcing mode) in the later logs, the SELinux context fix was critical. The earlier session had permissive=1 which is why some things worked before.

6. WebSocket Connections Keep Retrying The WebSocket connections to wss://stream-glb.osl.com were retrying every 4 seconds, indicating they were being caught by iptables but failing the SSL handshake through Burp.

Traffic Flow Summary

Without Proxy:
  Flutter (Dio) → Direct HTTPS → trade-glb.osl.com ✅
  Native (OkHttp) → Direct HTTPS → risk.checkout.com ✅

With iptables + Burp (System Cert Installed):
  Flutter (Dio) → iptables redirect → Burp → trade-glb.osl.com (Connection timeout due to Flutter's own SSL)
  Native (OkHttp) → iptables redirect → Burp → risk.checkout.com (Should work if SELinux is correct)

With WiFi Proxy + Burp:
  Flutter (Dio) → Ignores proxy → Direct connection (no interception)
  Native (OkHttp) → WiFi proxy → Burp → Servers (Works if cert is trusted)

Remaining Challenge: Flutter SSL Pinning

The Flutter layer in this app compiles its own certificate verification into libflutter.so. To fully intercept Flutter traffic, additional techniques would be needed:

  • reFlutter — Patches the Flutter binary to disable SSL verification
  • Frida — Runtime hooking to bypass ssl_crypto_x509_session_verify_cert_chain in libflutter.so

13. Lessons Learned

For Beginners

  1. Always check the app framework first. Flutter apps require different bypass techniques than pure native Android apps. Look for I flutter : in logcat to identify Flutter apps.

  2. System CA vs User CA matters. Production Android apps (API 24+) only trust system CAs by default. User-installed certificates won't work unless the app's network_security_config.xml explicitly allows them.

  3. SELinux context is as important as file permissions. On Android, having chmod 644 is not enough — files must also have the correct SELinux label. Always run chcon after placing certificate files.

  4. The tmpfs overlay trick is powerful. When you can't write to /system, mounting a tmpfs on top of a system directory lets you "replace" its contents without modifying the actual partition.

  5. Different HTTP stacks need different approaches:

    • Native Android (OkHttp, HttpURLConnection) → System cert store + proxy
    • Flutter/Dart → Needs Frida/reFlutter to patch libflutter.so
    • WebView (Chromium) → Uses its own cert validation (cr_X509Util)

  6. iptables vs WiFi Proxy:

    • WiFi Proxy: Apps must honor the proxy setting (many don't)
    • iptables: Forces ALL traffic through Burp, but requires invisible proxying mode
    • Best approach: Use both together

  7. The emulator's 10.0.2.2 is your gateway to the host machine's localhost. Always use this IP when configuring proxy settings on the emulator.

  8. tmpfs changes are lost on reboot. Keep your setup script handy — you'll need to run it every time the emulator restarts.

Key Takeaways for This Specific App (OSL)

  • The native layer (OkHttp for Checkout.com, Glide, Firebase) can be intercepted with the system cert + proxy approach
  • The Flutter layer uses Dart's HTTP client (Dio) which bypasses both the system proxy and system certificate store
  • Full interception of Flutter traffic would require Frida or reFlutter as an additional step
  • The app implements network_security_config that only trusts system CAs in release builds
  • WebSocket connections to stream-glb.osl.com also need SSL bypass for real-time data interception
